# Engineering guidelines

Rules for anyone writing code here, human or agent. They are ordered by what
breaks if you ignore them: correctness first, then structure, then style.

Three documents are normative and are **not** restated here — read them rather
than guessing:

| Document | Authority over |
|---|---|
| [`docs/design/architecture.md`](docs/design/architecture.md) | layering, data model, storage, time model |
| [`CONTRIBUTING.md`](CONTRIBUTING.md) | how to add a parser or resolver, the API surface, known traps |
| [`docs/design/GOAL.md`](docs/design/GOAL.md) | what is in scope and what is deliberately not |

If this file and `architecture.md` disagree, `architecture.md` wins and this
file is the bug.

---

## 1. The invariant that outranks everything

**Never invent an edge.** The only asset this tool has is that a user can trust
what it draws. An edge that might be right is worse than no edge, because it
costs a manual verification they didn't know they needed.

In code that means: when a signal is ambiguous, return nothing and
`ctx.count("rN.reason")` so the decline is visible. Every claim and edge carries
`file:line` provenance — if you can't cite it, you can't assert it. Confidence
values come from `config/confidence.yml`, never from a literal in a resolver.

This is the one rule where "it's probably fine" is never an acceptable answer.

### The same rule applies to what you say about the code

An unverified claim about this codebase is an invented edge. It costs the
reader the same thing — a verification they didn't know they needed — and it is
harder to catch, because prose carries no confidence score and no provenance.

So: **read the thing before describing it.** Not a similar file, not the same
API in another project, not your memory of this repo from earlier in the
session if it has been edited since.

Name the source of truth for the question actually being asked, because they
differ and they outrank each other:

| Question | Authority |
|---|---|
| what the design requires | `architecture.md` — normative, even where code disagrees |
| what the system actually does today | the code, and a test that runs |
| what a value is | `config/*.yml`, not a remembered number |
| why something is the way it is | git history, and `docs/design/architecture.md` §10 (decision record) |
| what an endpoint returns | the route in `backend/adduce/routes/`, or call it. `lib/api-spec/openapi.yaml` is now generated from the app and CI fails when it is stale, so it is answerable too — but the route is still the source |

**When the code and a document disagree, say so.** That divergence is a finding
in its own right and usually the most useful thing in the reply. Silently
picking whichever one supports your change discards it.

Two traps in this repo produce exactly this error:

- **Design documents written in the present tense.** `architecture.md` puts
  `GraphStore` in its layer diagram and defines `class GraphStore(Protocol)` in
  §3; §11.13 is the task to migrate `db/neo4j_client.py` onto it. It is the
  target, not the code. Asserting it exists today is wrong in the most
  expensive way — confidently, in the project's own vocabulary, to a reader
  with no reason to doubt it.
- **Scaffolding that looks like a contract** — fixed, and worth knowing how,
  because the shape recurs. `lib/api-spec/openapi.yaml` used to declare one
  path, `/healthz`, which the backend does not serve, while nothing imported
  the client orval generates from it: reading it returned a confident wrong
  answer. It is now generated by `backend/tools/export_openapi.py` and pinned
  by `tests/test_openapi_spec.py`, so its only possible error is staleness and
  CI fails on that. The UI's own contract is still hand-written —
  `frontend/src/lib/api.ts` against `frontend/src/lib/types.ts` — but no
  longer by trust: `tests/test_ui_contract.py` asserts every endpoint it calls
  against the routes actually served.

Where verifying is genuinely not possible, **state the assumption in one line
and keep working** — the prose equivalent of `ctx.count()`. A visible
assumption can be corrected by anyone who reads it. "Probably" and "should be"
are not verification; they are declines wearing the costume of an answer.

## 2. Where code goes

```
backend/adduce/parsers/     bytes + path → structured data.  Pure. No I/O, no DB.
backend/adduce/services/    extraction, claims, ingestion orchestration
backend/adduce/services/linker/   rN_*.py resolvers: claims → edges
backend/adduce/routes/      HTTP surface only — thin, no business logic
backend/adduce/db/          the only place that talks to Neo4j
config/*.yml             operator-tunable knobs (confidence, aliases, limits)
frontend/src/components/ views and widgets
frontend/src/components/ui/    vendored shadcn — do not hand-edit, regenerate
frontend/src/lib/        pure helpers: formatting, types, graph styling
frontend/src/store/      zustand state
lib/                     shared TS packages consumed across the workspace
```

**Dependencies point down, never up.** `core` logic imports nothing from the
layers above it; parsers may import core; only `db/` performs storage I/O;
nothing imports the UI. `architecture.md` §2 names the three files that
currently violate this — do not add a fourth.

A route handler that contains a `for` loop over graph nodes is in the wrong
file. Move the logic to a service and let the route call it.

## 3. File size: 300 lines, hard

**No production source file may exceed 300 lines.** Not a target, not a
guideline — the point at which you stop adding and start splitting.

The reason is not aesthetics. Long files here have always been two ideas
tangled together, and tangled ideas cannot be tested in isolation: you end up
constructing half the world to exercise one branch. Small files produce honest
test coverage; large files produce coverage theatre.

Scope of the rule:

- **Applies to** everything under `backend/adduce/`, `backend/tools/`,
  `frontend/src/` (excluding `components/ui/`), `lib/`, `artifacts/*/src/`,
  and `scripts/src/`.
- **Exempt:** vendored code (`frontend/src/components/ui/`), generated clients
  (`lib/api-client-react/src/generated/`), lockfiles, fixtures.
- **Tests** aim for the same limit but may run longer when a file maps to one
  module's behaviour. Past ~600 lines, split by behaviour area
  (`test_x_happy.py` / `test_x_declines.py`), not by line count.

### When a file approaches the limit

Splitting is not "cut it in half at line 150." Find the seam that already
exists and cut there. In order of preference:

1. **Extract a collaborator.** The file does two things; one of them is a
   noun. `gateway_parser.py` handling both route tables and path rewriting is
   a parser plus a `PathRewriter`.
2. **Extract the table.** Long dispatch chains, regex sets, language keyword
   maps and framework signatures are *data*. Move them to a module-level
   constant, a sibling `_patterns.py`, or a `config/*.yml` if an operator
   should be able to tune them.
3. **Extract per-variant modules behind a registry.** Five languages in one
   extractor is five modules and a lookup — the shape `parser_registry.py`
   already uses.
4. **Split the pipeline into stages.** `parse → normalise → emit` as three
   functions in three files, each independently testable.

For React, in order:

1. **Lift logic into a hook.** Data fetching, derived state and effects leave
   the component entirely (`useServiceMap`, `useGraphLayout`).
2. **Extract presentational children.** A panel, a legend, a row — anything
   with its own props contract.
3. **Move pure computation to `lib/`.** Layout maths, colour scales and
   formatters are not components and should never sit inside one.

Never split by creating `utils.py` or `helpers.ts`. A file named for its
grammatical role rather than its subject becomes a landfill within a month.
Name the module after what it *is*: `path_rewriter.py`, `confidence_scale.ts`.

### Files that already exceed the limit

31 production files do today — `ingest_claims.py` (1833),
`dependency_parser.py` (1475), `calibration.py` (1449), `GraphCanvas2D.tsx`
(869), and others. They predate the rule.

They are not a licence to add more. **When you touch a file that is already
over 300 lines, it must not get longer.** Add your change by extracting the
region you're working in — you have the context loaded, which is the cheapest
moment this split will ever be. Extracting more than you strictly need is
welcome; a drive-by rewrite of code you aren't otherwise touching is not, since
it buries the real change in a diff nobody can review.

## 4. Functions and classes

- **A function over ~30 lines wants splitting.** If you cannot name the piece
  you'd extract, you don't yet understand what it does.
- **A class that does two things is two classes.** The tell is a name with
  "and" in it, or a constructor that takes dependencies half the methods
  never use.
- **Four or more parameters wants a value object** — usually a frozen
  dataclass, which also gives the thing a name and a place for its invariants.
- **Return early.** Guard clauses at the top, happy path unindented at the
  bottom. Nesting past three levels is a refactor signal.
- **No boolean parameters that select behaviour.** `render(compact=True)` is
  two functions wearing a trenchcoat.

## 5. Duplication, and its opposite

**Two call sites repeating 3+ lines of the same logic become a shared helper.**
Before writing a helper, grep the module for one that already exists — a second
`normalise_host()` with slightly different edge cases is worse than none,
because now two behaviours disagree and neither is obviously wrong.

Duplicated *tests* count too. If a behaviour is covered, don't cover it again
from a different file; you have doubled the maintenance and added no signal.

**The counter-rule, which matters just as much:** do not abstract things that
merely look alike. Two parsers with similar shapes but different reasons to
change are two parsers. Ask whether they'd change *together*: if a requirement
shift would edit both, share the code; if it would edit one, leave them apart.
Premature abstraction is more expensive to unwind than duplication is to fix,
because it couples modules that had no business knowing about each other.

When you do extract, extract the *decision*, not the syntax. A helper that
takes six flags to reproduce its callers' variations has abstracted nothing.

## 6. Designing for what comes next

The roadmap splits this into a library and a server (`GOAL.md`). Code written
today should not have to be unpicked to get there.

- **Depend on protocols, not implementations.** Storage is reached through
  `db/`, and is on its way to the `GraphStore` protocol defined in
  `architecture.md` §11.13. A service that imports the Neo4j driver directly
  cannot be used by a host that has no Neo4j, and will have to be rewritten
  when that protocol lands — so don't write one now.
- **Extend by registration, not by editing a switch.** New parsers register in
  `parser_registry.py`; new resolvers are `rN_name.py` exposing
  `resolve(index, ctx)`. Adding a capability should add a file, not edit five.
  If your change requires editing a dispatch chain in three places, the
  extension point is missing — add it.
- **Values that operators tune live in `config/*.yml`**, not in source.
  Confidence, aliases, internal namespaces, promotions and limits are all
  deployment decisions. Limits the UI must honour are served from
  `/api/config` so a deployment can change them without a rebuild.
- **Keep the pure layers pure.** Parsers and resolvers take data and return
  data. No clocks, no network, no environment reads, no globals. This is what
  makes them deterministic, testable, and embeddable — and determinism is a
  shipped guarantee, not a convenience.
- **Add the new edge type in one change**, across resolver, writer allowlist
  and tests. The writer is fail-closed: one unregistered type rejects the
  entire link run.
- **Don't build for imagined requirements.** Extensibility means seams in the
  right places, not configuration for a feature nobody asked for. The test is
  whether a plausible next requirement lands as an addition rather than a
  rewrite — not whether every knob is already exposed.

## 7. Naming, comments, errors

**Names.** Say what the thing is in the domain's vocabulary: `claim`,
`rendezvous key`, `resolver`, `evidence`, `edge`. Consistency with the existing
lexicon beats a cleverer word. Node ids never contain line numbers — line
numbers are evidence, so editing a file above a claim must not churn identity.

**Comments are exceptions, not narration.** Write one only for a non-obvious
constraint, an invariant, an operational risk, or an external bug. Prefer a
clearer name or a smaller helper over an explanatory comment. A comment that
restates the code is noise; one that records the trap you fell into is worth
more than the fix. Delete stale comments when you move code. No tracker or task
IDs in source — those belong in the tracker.

**Errors.** Parsers return `None` for files they don't recognise; they never
raise for unrecognised input. Anything unexpected fails loudly with the file
and line in the message. Never swallow an exception to keep a run alive without
counting it — a silent skip is indistinguishable from a clean pass. Never
`print` a secret; redaction happens centrally in `add_claim`, and it stays
there so a new emitter cannot forget it.

---

## 8. Tests

- **New behaviour needs a test.** `backend/tests/` is plain pytest, no
  fixtures framework beyond what's there.
- **Cover the declines.** The happy path is the easy half; this project's
  correctness lives in what it *refuses* to assert. Test that an ambiguous
  signal produces no edge and increments its counter.
- **Test through the seam you built.** If a split was worth doing, the new
  module is testable without constructing a graph or a database.
- **Don't add a test file for behaviour already covered elsewhere**, and don't
  add a helper file that removes no duplication and enforces no limit.

## 9. Before you call it done

```bash
.venv/bin/python -m pytest backend/tests -q
```

```bash
pnpm --filter @adduce/web run typecheck
```

If you touched extraction or linking, re-ingest a repo and run the accuracy
harness — it catches regressions unit tests structurally cannot, because it
compares the graph against real source. The harness reads the **stored** graph,
so re-ingest first or you will be measuring the old code's output.

```bash
python scripts/accuracy/verify_edges.py && python scripts/accuracy/measure_recall.py
```

Then check your own diff against this file: no source file over 300 lines, no
logic duplicated at two call sites, no new layering violation, no comment that
restates its code, and a test for every behaviour you added.
